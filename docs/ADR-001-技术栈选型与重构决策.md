# ADR-001 技术栈选型与重构决策

- **状态**：✅ **已采纳（Accepted，2026-10-16，全部待决项已锁定）**
- **日期**：2026-10-16
- **决策范围**：FayeLong 英语学习网站的前端框架、后端语言/框架、任务与数据层演化路线
- **提出背景**：网站处于早期版本，作者自评主力技术栈为 Java + Vue，实际使用 Python（偶尔）与 React（多年前接触过）；计划新增雅思真题模拟训练与多题型单项训练
- **执行计划**：见 `docs/REFACTOR-PLAN-001-执行计划.md`（本 ADR 的施工派生文件）

> 本文所有规模、依赖、结构数据均实测自当前仓库（`D:/code/FayeLong`，main 分支，v1.14），非估算。

---

## 0. 结论摘要

| 层 | 决策 | 理由一句话 |
|---|---|---|
| **前端** | ✅ **React 18 → Vue 3 重写** | 收益真实（作者生产力 = 一等架构属性），成本可控（23 文件 / 7,564 行，API 契约已冻结），风险低（后端零改动） |
| **后端语言** | ❌ **不换 Java，保持 Python/FastAPI** | 换 Java 买不到「稳定/健壮/可扩展」，却引入**双运行时 + Python sidecar**，技术栈复杂度上升而非下降 |
| **后端架构** | ✅ **必须加固（5 项债）** | 真正的可扩展性瓶颈在数据模型形状、迁移机制、任务模型、测试网，与语言无关 |
| **ASR 引擎** | ❌ **不动** | `faster-whisper`/`ctranslate2` 无 Java 等价物，是**不可迁移资产** |

**一句话**：把「重构」拆成「换前端框架（做）」+「换后端语言（不做）」+「加固后端架构（做，且比换语言重要得多）」。

### 1.2 依赖面（本次评估最关键的发现）

**后端第三方依赖总共 5 个，全是「Web 骨架」，其余 100% 标准库：**

```
fastapi / uvicorn / sqlalchemy / pydantic-settings / python-multipart
```

全量 import 扫描结果，除上述 5 个外只有：`asyncio base64 collections concurrent contextlib dataclasses datetime difflib functools hashlib hmac json logging mimetypes os pathlib re secrets shutil sqlite3 subprocess sys tempfile threading time typing urllib wave`

**ML 依赖被单独隔离在 `requirements-ml.txt`，且 `services/asr.py` 是延迟导入**：
`faster-whisper / ctranslate2 / huggingface-hub / onnxruntime / numpy / lemminflect`

**前端运行时依赖 5 个**：`react 18 / react-dom / react-router-dom 6 / @tanstack/react-query 5 / zustand 5`；构建侧 `Vite 5 + TS 5.6 + Tailwind 3 + PostCSS`。

> **推论**：当前后端本质上是「标准库 + SQLite + subprocess(ffmpeg) + 轻量 Web 框架」。它不是「重 Python 生态锁定」，真正的语言锁定**只有一个点：ASR**。

### 1.3 架构特征

| 维度 | 现状 | 评价 |
|---|---|---|
| 部署形态 | 单端口单体：FastAPI 同时托管前端静态产物（`STATIC_CANDIDATES` → `frontend/dist` 或 `static/`） | 良好，简单可靠 |
| API 面 | **35 个 REST 端点**（`GET /{media_id}/stream` 支持 Range、`GET /status` 走 SSE） | 契约清晰，已具备冻结条件 |
| 数据模型 | **9 张表**：`categories / media / sentences / attempts / notes / vocab / settings / users / translations` | 形状是**「听写专用」**（见 §2） |
| 任务模型 | 进程内 `ThreadPoolExecutor`（2 线程）+ DB 状态机字段；启动 `requeue_unfinished()` 自愈 | 可用，但**无任务表、无独立 worker、无跨进程队列** |
| 迁移机制 | `create_all` + **手写** `_ensure_columns()` 幂等 `ALTER`（已手工补 2 列）+ `_ensure_indexes()` | ⚠️ 无 Alembic，**随表数增长必然失效** |
| 认证 | HMAC 签名 cookie + 中间件默认拒绝；PBKDF2-HMAC-SHA256（零新增依赖） | 良好 |
| 测试 | **无 pytest、无单元测试**；仅 `scripts/verify_*.mjs` 8 个 CDP 端到端脚本 | ⚠️ 第二大风险 |

### 1.4 交付链约束（重构的隐藏成本所在）

- **路线 A — Windows 便携包**：`packaging/build.ps1` 10 步，打包 **embed Python 3.13.14 + 全依赖 + 便携 ffmpeg + VC++ DLL（5 个）+ whisper small 模型 + ECDICT 全量**。产物 zip ≈816 MB / 解压 1.72 GB。目标机是**无开发环境的 8GB Windows 笔记本，小白式安装（拷文件夹 → 双击 → 用浏览器）**。
- **路线 B — 腾讯云**：Ubuntu 24.04 轻量实例 **2 vCPU / 2 GB**，systemd + venv + uvicorn 单 worker，源码原生部署。
- **关键资产**：涉及 `python313._pth` isolated 模式、`msvcp140` 缺失、SQLite 无迁移框架、zip 中文名、`SO_REUSEADDR` 误判等**一整套已踩平的坑**。这些知识不随语言迁移，换栈 = 全部重踩。

## 2. 需求侧推演：新功能会冲击哪里

### 2.1 计划新增

1. **雅思真题模拟训练**：一整套卷 —— Listening 4 parts / 40 题、Reading 3 passages / 40 题、Writing 2 tasks、Speaking 3 parts；限时、按 section 提交、自动判分、完整成绩报告。
2. **多题型单项训练**：现有「导入音频听写」= 一种单项训练；后续阅读理解、判断题（TFNG）、标题匹配、句子填空、写作批改等。

### 2.2 冲击点矩阵（★ = 真实风险）

| # | 冲击点 | 现状 | 严重度 |
|---|---|---|---|
| a | **数据模型形状不匹配** | `Sentence` 强绑 `start_ms/end_ms/clip_path`（音频时间轴）。阅读理解需要「文章 → 段落 → 题组 → 题目 → 选项 → 答案」，塞进现有表会污染 | ★★★ |
| b | **判分逻辑未抽象** | `services/dictation.py` 是听写专用纯函数（归一化 + 词级 diff）。判断题/选择题/填空/写作各有判分器，需要策略化 | ★★★ |
| c | **作答记录绑死题型** | `attempts.sentence_id` 外键硬绑句子 | ★★ |
| d | **无考试会话实体** | 模拟考需要「会话」（开始时间、剩余时间、分 section 暂存、交卷、成绩单），当前无此概念 | ★★ |
| e | **任务模型不分负载类型** | ASR 是 CPU 密集长任务（分钟级）；将来 LLM 写作批改是网络 IO 密集。同池 2 线程混跑会互相饿死 | ★★ |
| f | **迁移机制将失效** | 表数 9 → 20+，手工 `_ensure_columns` 不可维护 | ★★ |
| g | **SQLite 单写** | 模拟考高频写 + SSE 轮询 | ★（个人单用户，可接受） |

**★ 的分布说明**：**a–f 六项全部与「语言」无关**，它们分别属于数据建模、服务分层、任务编排、工程基建。

## 3. 决策分析

### 3.1 【批判性分析】拆掉原始前提

原问题的因果链是：

> 为了**稳定性、健壮性、可扩展性** ⟹ 需要**重新选型技术栈**

这条链在架构上不成立。按对实际结果的影响排序，「稳定/健壮/可扩展」的决定因素依次是：

| 排序 | 决定因素 | 当前状态 | 换语言能否改善 |
|---|---|---|---|
| 1 | 数据模型与领域边界是否匹配 | ⚠️ **不匹配**（§2.2 a/c/d） | ❌ 无关 |
| 2 | 是否有自动化测试网 | ❌ **没有单测** | ❌ 无关 |
| 3 | 任务/并发模型是否匹配负载 | ⚠️ 勉强（§2.2 e） | ❌ 无关 |
| 4 | 迁移与演化机制是否可靠 | ⚠️ 手工（§2.2 f） | ❌ 无关 |
| 5 | 交付链是否稳定 | ✅ 已跑通两条 | ❌ 无关（换栈则**退化**） |
| 6 | Web 框架与语言 | ✅ 依赖仅 5 个，够用 | ✅ 唯一能改的一项 |

**换语言能改变的只有排第 6 的项 —— 而它在风险清单里排最后。** 换句话说：现在的稳定性风险不在 Python，在「没有测试」和「模型形状绑死听写」。

### 3.2 但有一个论据是真实的：bus factor = 1

不能忽略：**作者对 React 几乎无经验、Python 只是偶尔使用**。可维护性是架构质量的一等属性，不是软指标。

这个论据成立的，但它支持的是**「前端换 Vue」，不是「后端换 Java」**：
- **前端** 7,564 行是作者**每天都要改**的地方（加题型、改页面）。React 熟练度直接决定迭代速度 ⟹ 换 Vue 收益真实。
- **后端** 5,739 行中语言相关表面极小（5 个骨架包）；而**最难的资产全在这里**（ASR 管线、词典三级优先、听写判据、音频切片、打包链）。换语言 = 把最难的部分重写一遍，把最容易的部分换掉。

> **换语言换掉的是容易的部分，留下的是难的部分 —— 方向反了。** 正确的做法是「难的部分原地加固，容易的部分换成作者熟练的」。

### 3.3 【硬核验】Java 后端方案到底能不能成立

不能只讲感觉，逐项验证：

| 验证项 | 结果 |
|---|---|
| **ASR 能否迁到 Java 进程内？** | ❌ 不能。`faster-whisper` 基于 `ctranslate2`（C++ 扩展），**只有 Python binding**。替代路径是 whisper.cpp + JNI/FFM（另一套生态），需重新验证英文标点、词级时间戳、Silero VAD —— 这些正是当前句子切分精度的基础 |
| **词形还原能否迁？** | ❌ `lemminflect` 是 Python 包，Java 无对应，需自行实现规则（词典三级优先查询依赖它做候选验证） |
| **能否实现「单一技术栈」？** | ❌ **不能**。ASR 必须留 Python ⟹ 结果是 **Java + Python sidecar + Vue**，比现在（Python + Vue）**更复杂**。原始动机不可达 |
| **Windows 便携交付成本？** | ⬆️ 上升。需 jlink/jpackage 运行时 **加上** Python sidecar 运行时 = **双运行时**，1.72 GB 只会更大，「小白式安装」变复杂 |
| **云端内存？** | ⚠️ 高风险。实例仅 **2 GB**，whisper small int8 常驻约 1 GB 量级，再叠加 JVM 基线（约 250–400 MB）余量极小。（此条为**方向性判断，需实测确认**，不应作为唯一否决依据） |
| **工期？** | 重写 5,739 行 + sidecar + 打包链重构 + 重踩全部坑，**4–6 周**，期间零新功能产出 |
| **能买到的收益？** | 仅「作者熟悉」。而 §2.2 的 6 项真实风险**一项都没解决** —— 反而要在 Java 里重新解决（Flyway/Quartz 确实是成熟方案，但那是在为「重写」找理由，不是在为「改进」找理由） |

**结论：Java 后端方案的 ROI 为负。**

### 3.4 分层决策

| 层 | 语言 | 技术栈 | 决策 |
|---|---|---|---|
| **UI 层** | TypeScript | **Vue 3.5 + `<script setup>` + Vue Router 4 + Pinia 2 + @tanstack/vue-query 5 + Vite 5 + Tailwind 3** | ✅ **重写**（框架更替，语言不变） |
| **API / 领域层** | Python | **保持 FastAPI，做分层加固 + 题型插件化** | ✅ **保留 + 加固** |
| **计算引擎层** | Python | **faster-whisper / ffmpeg / ECDICT 原地不动** | ✅ **冻结** |

技术栈数量：**现状 3（Python / TS-React / ...）→ 决策后 2（Python + TS/Vue）→ Java 方案将变成 3 且含双运行时。**

## 4. 决策

> **决策 D1**：**不进行全栈重构。**
> **决策 D2**：前端 **React → Vue 3 全量重写**，趁 UI 面小（23 文件）一次性完成，硬切换，旧版冻结在 git tag。
> **决策 D3**：后端 **保持 Python/FastAPI**，同步偿还 5 项架构债（§5.2），优先级高于任何新功能。
> **决策 D4**：ASR / ffmpeg / 词典三处**不改动**。
> **决策 D5**：为 IELTS 引入**题型插件化 + 新表族**，现有 `media/sentences/attempts` 视为「听写题型」的私有实现，**不做数据迁移**。

### 5.1 P0 冻结 API 契约（2 天）— 一切重写的前提

Vue 重写之所以低风险，唯一原因是**后端不动**。因此必须先把契约固化。

1. 从 FastAPI 导出 OpenAPI：`GET /openapi.json` → 落盘 `contracts/openapi-v1.json` 作为基线快照。
2. 用 `openapi-typescript` 生成 `contracts/api-types.d.ts` —— **替换掉手写的 699 行 `client.ts` 类型部分**（这是本次重构**顺手赚到的**最大好处：类型从手工维护变为契约自动生成）。
3. 写契约校验脚本 `scripts/check-contract.mjs`：重新导出 OpenAPI 与基线 diff，任何端点变更必须显式评审。**这是防「前后端漂移」的唯一机制。**
4. **建测试网（与 P3 共享）**：
   - `pytest` 覆盖**纯函数层**（最高回归风险、零依赖）：`services/dictation.py`（归一化 + 判据）、`services/dict.py`（三级优先 + 词形还原）、`services/marks.py`（load/dump 归并夹取）、`services/study.py`（统计）。目标覆盖率 ≥90%。
   - `fastapi.testclient` + 临时 SQLite：覆盖媒体状态机流转、`requeue_unfinished` 自愈、未登录 401 守卫。
   - 保留 `scripts/verify_*.mjs` CDP 端到端作为 UI 验收。

> **验收**：`pytest` 全绿；`check-contract` 能捕获人为改动；OpenAPI 基线入库。

---

### 5.2 P1 Vue 骨架 + 基础设施（2 天）

依赖映射（**逐项 1:1 对位，无架构风险**）：

| 现（React） | 新（Vue 3） | 迁移成本 |
|---|---|---|
| `react` 18 | `vue` 3.5 + `<script setup>` | — |
| `react-router-dom` 6 | `vue-router` 4 | 低（**5 条路由**） |
| `zustand` 5 | `pinia` 2 | 低（**1 个 store，约 80 行**，API 近乎同构） |
| `@tanstack/react-query` 5 | `@tanstack/vue-query` 5 | 低（**96 处调用点**，同一 `@tanstack` 家族，API 同构，机械替换） |
| `JSX` | SFC `<template>` | 机械（**635 处 `className` → `class`**） |
| Vite 5 / TS 5.6 / Tailwind 3 / PostCSS | **完全不变** | **零** |

**可以近乎免费复用的部分（约 1,300 行 / 17%）**：
- `api/client.ts` 的 699 行中，**请求封装与全部 interface 类型是纯 TS**，与框架无关 —— 类型改由 P0 自动生成，只重写 `request()` 与 SSE/上传封装。
- `components/icons.tsx`（465 行 SVG）→ 直接搬进 SFC。
- `utils/format.ts`、`utils/speech.ts`（113 行）→ **零改动**。

**基础设施清单**：
1. `frontend-vue/` 目录 + Vite 脚手架（**不覆盖旧目录，保证可回滚**）。
2. 统一请求层：`request()` 封装保留 `UNAUTHORIZED_EVENT` 事件语义（换成 Vue 的全局事件总线/mitt 或 Pinia action）。
3. `Layout` 三段式移动端外壳（`flex h-dvh flex-col overflow-hidden` + `shrink-0`/`flex-1 min-h-0 overflow-y-auto`）—— **Tailwind class 可整体照搬，但必须重测手机顶栏换行**（这是历史上踩过的坑）。
4. 32px 触摸目标规范、`ErrorBoundary` → `onErrorCaptured`。

### 5.3 P2 页面逐页迁移（6–8 天）

按「依赖少 → 依赖多」排序，每页独立可验收、可并行取舍：

| 顺序 | 页面 / 模块 | 行数 | 工期 | 难点标注 |
|---|---|---|---|---|
| 1 | `LoginPage` | 151 | 0.5 | 无 |
| 2 | `Layout` + `PlayerBar` + `store/player.ts` + `bindAudioElement` | 232+197+80 | 1–1.5 | 全局 `<audio>` 元素注册模式 |
| 3 | `MediaLibraryPage` + `CategoryManager` + `CategoryChips` | 1162+334 | 2–3 | 上传进度、SSE 订阅、拖拽排序 |
| 4 | `StudyPage` + `DictationBox` + `ClickableText` + `SentenceStage` + `WordPopover` + `NoteEditor` + `NotesPanel` + `DiffResult` | 1683+295+155 | **3–4** | **占前端 45% 工作量**，见下 |
| 5 | `VocabPage` + `VocabPracticePage` | 363+861 | 2 | 纯前端练习逻辑 |
| 6 | 移动端全量回归 + CDP 脚本重跑 | — | 1 | `verify_mobile` / `verify_v1_12` / `verify_marks` 等 |

**StudyPage 的三个真实难点（不是 React 知识，而是重写风险）**：
1. **`useClipPlayer.ts`（205 行）→ Vue composable**：内部逻辑是**原生 `HTMLAudioElement` API**（`timeupdate`/`loadedmetadata`/`ended`/`error` 事件、A-B 循环、与整段播放互斥），**与框架无关，可近乎逐行照搬**；只需把握手方式从 `useState/useRef/useCallback` 换成 `shallowRef/reactive + onMounted`。**这是最容易被高估的难点 —— 实际很低。**
2. **输入框交互**：中文输入法 `compositionstart/end`、`Enter` 提交与「下一题」按钮的**双触发坑**（历史已知：按钮不能 `autoFocus`）—— **必须重新验证，不可假定照搬成功**。
3. **`ClickableText` 的「易听错」标记**：与后端 `sentences.marks` 的**分词正则必须与后端 `services/marks.py` 保持一致**，否则词序下标错位。**这是一处隐藏的一致性契约，重写时务必对照。**

### 5.4 P3 后端 5 项架构债（4–5 天）— 比换语言重要得多

| # | 债务 | 改造方案 | 工期 |
|---|---|---|---|
| **D1** | 无迁移框架 | 引入 **Alembic**（SQLite 用 `batch_alter_table`）。**现在是 9 张表，是最便宜的引入时机**。将现有 `_ADDED_COLUMNS`/`_INDEXES` 转为基线迁移，`_ensure_columns` 降级为「老包就地更新」的兼容垫片 | 1 |
| **D2** | 任务模型绑进程 | 新增 **`jobs` 表**（`kind / ref_id / status / progress / error / priority / payload / created_at / started_at / finished_at`）+ 独立 worker 入口 `python -m app.worker`。把 `requeue_unfinished()` 泛化为「jobs 表的崩溃恢复」。**现有 `ThreadPoolExecutor` 保留为进程内执行器，不推翻** | 1.5 |
| **D3** | 负载类型混跑 | **按负载分池**：CPU 池（ASR/ffmpeg，线程数 = 物理核数）与 IO 池（翻译 / 将来 LLM 批改，可高并发）。避免长 ASR 饿死翻译 | 含 D2 |
| **D4** | 无测试网 | 见 P0.4（已计入 P0） | — |
| **D5** | 领域边界未分层 | 在 `services/` 之上明确 **题型插件层**（见 P4），使 `api/` 只做协议转换，不承载领域规则 | 1 |
| **D6** | 可观测性缺失 | 结构化日志 + `/api/health` 增加 jobs 积压、模型就绪、磁盘余量字段（**不引入重监控栈**，保持零付费） | 0.5 |

> **验收**：老库能被 Alembic 正确 upgrade；杀掉 worker 进程后重启能自动恢复未完成任务；ASR 与翻译并发不再互锁。

### 5.5 P4 题型插件化 + IELTS 数据模型（3–5 天）

#### 5.5.1 题型插件契约

后端目录 `backend/app/services/question_types/`，每个题型一个模块，统一注册表：

```python
@dataclass(frozen=True)
class GradeResult:
    score: float          # 得分
    max_score: float      # 满分
    correct: bool         # 是否判对（用于「已掌握」等语义）
    detail: dict          # 词级 diff / 逐空对错 / 评分细则，供前端渲染

class QuestionType(Protocol):
    code: str             # "dictation" | "reading_mcq" | "tfng" | "matching"
                          # | "gap_fill" | "sentence_completion" | "writing"
    def validate(self, payload: dict) -> None: ...          # 题目数据合法性
    def grade(self, answer: dict, response: dict) -> GradeResult: ...  # 唯一判分入口
    def normalize(self, response: dict) -> dict: ...         # 归一化（大小写/标点/空白）
```

- 现有 `services/dictation.py` 的纯函数**直接包装成 `dictation` 题型**，逻辑零改动。
- 注册表通过 **`GET /api/question-types`** 下发给前端，避免前后端题型清单漂移。
- 前端 `frontend-vue/src/question-types/` 与之对位：每个题型 = 一个**作答组件 + 一个结果渲染组件**，按 `code` 动态挂载。

> 这是本次方案中**唯一真正解决「可扩展性」的改造**：新增「阅读理解」= 新增一个题型模块，而不是修改核心。

#### 5.5.2 IELTS 数据模型（新表族，不动旧表）

```
papers            试卷（title, mode=full_mock|section_drill, source, tags）
  └ sections      分卷（paper_id, kind=listening|reading|writing|speaking,
                          ordinal, time_limit_sec, instructions）
      ├ passages  阅读文章（section_id, ordinal, title, body_md）  ← 听力 section 走 media_id 复用现有音频
      └ questions 题目（section_id, passage_id?, ordinal, type, stem,
                       options JSON, answer JSON, explanation）
                        answer 用 JSON 而非散列：不同题型答案形状不同
                        （选择="A" / 多选=[...] / 填空=[可接受答案] / 写作=范文+评分标准）

practice_sessions 作答会话（paper_id 或 draft_kind, started_at, submitted_at,
                            status, time_spent_sec）
  └ responses     逐题作答（session_id, question_id, user_answer JSON,
                            score, max_score, graded_at, detail JSON）
```

**关键设计取舍（务必保留）**：
- ✅ **不改 `media/sentences/attempts`**。现有听写在 `questions` 中以 `type='dictation'` + `ref_sentence_id` 指向 `sentences.id` 表达，**历史数据零迁移、零风险**。
- ✅ **`answer` / `detail` 用 JSON 列**：题库题型形态差异极大，硬拆列会不断 `ALTER TABLE`（正是 D1 债务的成因）。
- ✅ **`sections.time_limit_sec` + `sessions` 承载限时与交卷**，不污染媒体状态机。
- ⚠️ **`media.status` 状态机保持原样**：它是「素材处理」状态，考试会话状态是另一条轴，**不要合并**。

#### 5.5.3 新增端点（示例，与现有 35 个端点风格一致）

```
GET    /api/papers                      试卷列表
GET    /api/papers/{id}                 试卷结构（含 sections/questions）
POST   /api/papers/{id}/sessions        开始一次作答
PATCH  /api/sessions/{id}/responses     暂存作答（支持分 section 提交）
POST   /api/sessions/{id}/submit        交卷判分
GET    /api/sessions/{id}/report        成绩报告
GET    /api/question-types              题型注册表下发
```

### 7.1 Q6 决策对架构的强制约束（重要）

锁定「外部 AI 批改 + 2 GB 不升配」后，题型契约**必须**支持异步判分。原方案中的

```python
def grade(self, answer: dict, response: dict) -> GradeResult: ...
```

对写作题型**不可用** —— 一次批改是数秒级的外部网络调用，不能同步阻塞请求线程。因此对 ADR 正文 §5.5.1 做如下**修订**：

```python
class QuestionType(Protocol):
    code: str
    # 判分模式：'sync' = 纯函数即时判分；'async' = 必须走 jobs 表 + IO 池
    grade_mode: Literal["sync", "async"]

    def validate(self, payload: dict) -> None: ...
    def normalize(self, response: dict) -> dict: ...
    # sync 题型实现此方法
    def grade(self, answer: dict, response: dict) -> GradeResult: ...
    # async 题型实现此方法（在 worker 中执行）
    def grade_async(self, answer: dict, response: dict) -> GradeResult: ...
```

由此衍生 4 条**强制设计约束**：

| 约束 | 说明 |
|---|---|
| **1. 判分走 jobs 表** | 写作批改是一个 `kind='grade_writing'` 的 job，由 **IO 池**执行（印证 P3-D3 分池的必要性）。交卷请求只入队并返回 `status='grading'`，前端轮询/SSE 取结果 |
| **2. 结果必须缓存** | 同一 `(question_id, normalized_response)` 的批改结果落库缓存，**避免重复付费**。参照现有 `translations` 表的缓存模式（key = sha1） |
| **3. 必须有降级路径** | 外部服务不可用/超配额时，写作题降级为「返回参考范文 + 评分标准 + 自评清单」，`status='degraded'` 而非失败。**绝不能因为第三方挂了导致交卷不可用** |
| **4. 零密钥不入库** | API Key 走环境变量（`FAYELONG_*`，与现有 `Settings` 一致），**不写入 `data/`、不写入数据库**。云端在 systemd unit 注入 |
| **5. 成本可控** | 按 session 记录调用次数与 token 用量，落 `settings` 或独立计数表；超阈值时拒绝并提示（个人自用，需有硬上限） |

> **对 Q6 的冷静提示**：外部 AI 批改引入了**付费依赖**，这与项目「零付费依赖」的既有定位冲突。这是 Q6 决策的**已知代价**，需要你认可：写作批改将成为全站**唯一**的付费点（且依赖外网）。若希望维持零付费，备选是「只给参考范文 + 评分标准，不做自动批改」——建议在 P4 开工前再确认一次。

## 8. 决策影响公示（本 ADR 明确**不做**什么）

为避免范围蔓延，以下事项**明确排除**在本次重构之外：

- ❌ 不换后端语言、不引入 JVM、不引入 Python sidecar
- ❌ 不改动 ASR / ffmpeg / ECDICT 三处引擎与其配置
- ❌ 不重写 Windows 打包链（`packaging/build.ps1` 与 embed Python 方案保持）
- ❌ 不做历史数据迁移（`media/sentences/attempts` 原地保留）
- ❌ 不引入重监控栈（保持零付费：结构化日志 + `/api/health` 扩展字段即可）
- ❌ 不在此期间开发任何 IELTS 新功能（Q2 锁定）
- ❌ 不长期并行维护 React 与 Vue 两套前端（切换即冻结旧版）

## 附：结论一句话

> **不要为了「作者熟悉」去重写最难的部分。**
> 把每天都要改的前端换成你熟悉的 Vue（23 文件，低成本，高回报），
> 把决定可扩展性的后端架构债偿清（数据模型、迁移、任务、测试），
> ASR 与打包链原地不动。
> 这样得到的是 **2 个技术栈（Python + Vue）**，而不是 Java 方案的 **3 个技术栈 + 双运行时**。
