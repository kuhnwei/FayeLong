## 本轮换来的纪律（写进计划 §0 / P3-6）
1. **构建期改写过的文件不能用直接 `cmp`**：`build.ps1` 对 `使用说明.txt` 做占位符替换 + CRLF，对**所有 bat** 也做 CRLF。判据是归一化后比——这条**连续坑了两次**（我先错判 `使用说明`，再错判 bat）
2. **重试组语义必须分开**：`already exists`（幂等）vs `readonly/locked`（瞬时）。**绝不把 `disk I/O error`/`no such table` 塞进去**
3. **`table notes already exists` 这条记录不可复现**：QA 12 进程×5 轮 + 毫秒屏障 80+ 次未复现，仓库/产物/日志无残留 → docstring 只留「机制推断 + readonly/locked 类实验复现」，**不再声称复现过那个具体报错**
4. **少而高并发 ≫ 多轮低并发**：G2 用例从 4 进程×4 轮（11.7s，命中 67%）改成 **8 进程×1 轮（5.07s，未修版 3/3 全红）**。4 进程时争抢不激烈，单进程失败率只 14%
5. **`with sqlite3.connect(...)` 只提交事务、不关闭连接**（不是 `contextlib.closing`）→ Windows 上文件仍被持有，`rmtree(ignore_errors=True)` 静默删不掉

## 三条「断言无牙」的教训
1. **G1 的 `[job:A]` 日志比对是恒真的**：worker 执行线程上除上下文内部外**没有任何日志**，所以「B 开始后不得出现 `[job:A]`」永远成立。QA 做定向变异（只 set 不 reset）→ 用例仍绿。修法：**向跑过 A/B 的那个 executor 提交 `current_job_id()` 探针**，断言返回 `None`。变异后返回 `'2'` → 红
2. 工程师修 G1 时自己也踩了一个：探针变量名与断言③里的同名列表推导撞车 → 断言永远读到 `[]`，改名后才绿
3. **确定性守卫与统计性守卫要分清**：G2 集成用例是统计性的（单次不保证红），确定性守卫是参数化单测；docstring 必须写明，否则后人会把偶发绿当成「修复失效」
